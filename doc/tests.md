# Tests

## Running the tests

Download the test instances (the `tests` archive of the data, see `data/data.json`):
```shell
python3 scripts/download_data.py --archives tests
```

Build and run the tests:
```shell
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DBATCHSCHEDULINGSOLVER_USE_HIGHS=ON
cmake --build build --config Release --parallel
ctest --test-dir build/test --build-config Release --parallel --output-on-failure
```

The MILP algorithms need an MILP solver (`-DBATCHSCHEDULINGSOLVER_USE_HIGHS=ON`): without one, they throw and their tests fail. The tests run from the root of the repository, which contains `data/` and `test/`.

To run the tests of one algorithm, filter them by name with `-R`:
```shell
ctest --test-dir build/test -R MilpRankBasedTwoIndex --output-on-failure
```

or run the test executable directly, with a gtest filter, to see the output of the algorithm:
```shell
./build/test/algorithms/BatchSchedulingSolver_milp_rank_based_test --gtest_filter='MilpRankBasedTwoIndex/*'
```

The CI (`.github/workflows/build.yml`) downloads the `tests` archive, builds with HiGHS and runs all the tests on Linux, macOS and Windows.

## Test instances

The test instances are generated by `scripts/generate_data.py` (with `install/bin/batchschedulingsolver_generator`), in `data/tests/<objective>_<environment>/` or `data/tests/<objective>_<environment>_release_dates/`, and listed in `data/test_<objective>_<environment>.txt` or `data/test_<objective>_<environment>_release_dates.txt`.

The objectives are `makespan`, `total_flow_time` (`tft`), `total_weighted_flow_time` (`twft`), `total_tardiness` (`tt`), `total_weighted_tardiness` (`twt`) and `throughput`. The environments are:
* `single`: one machine;
* `parallel`: 2 to 5 identical parallel machines (machine-independent processing times);
* `unrelated`: 2 to 5 unrelated parallel machines.

An instance `tft_n3x2x4_release_dates_s1` has 3 machines, 2 batches per machine and 4 jobs per batch (24 jobs), release dates, and seed 1. All the machines have a capacity of 100. The processing times are in $[1, 100]$, and the weights are 1, or in $[1, 100]$ for the weighted objectives and the throughput. The generator uses a release date dispersion factor of 0.5 (or 0 without release dates) and a due date tightness factor of 0.5.

`data/test_makespan_identical_sizes.txt` lists single machine makespan instances where all the jobs have the same size.

The instances are published in a GitHub release. To change them, regenerate them, publish a new archive with `scripts/create_data_archives.py`, and update `data/data.json`.

## Writing tests

The tests of an algorithm are in `test/algorithms/<algorithm>_test.cpp`, with the helpers of `test/algorithms/tests.hpp`, and are declared in `test/algorithms/CMakeLists.txt`.

The tests are `ExactAlgorithmTest`: on the generated test instances, check that the algorithm finds the optimal value. The instances are listed in `test/algorithms/<algorithm>_test.txt`, one per line, with their path relative to `data/`. The reference is the optimal solution stored as the certificate `data/<instance path>_solution.json`, read with `get_solution`.

Add the file to the sources of the test executable in `test/algorithms/CMakeLists.txt`.

The body of the test is written in each test file, since it depends on what the algorithm proves:
```cpp
TEST_P(ExactAlgorithmTest, ExactAlgorithm)
{
    TestParams test_params = GetParam();
    const Instance instance = get_instance(test_params.files);
    const Solution solution = get_solution(instance, test_params.files);
    auto output = test_params.algorithm(instance);
    EXPECT_EQ(output.solution.feasible(), true);
    EXPECT_EQ(output.solution.objective_value(), solution.objective_value());
    // If the algorithm proves optimality:
    EXPECT_EQ(output.bound(), solution.objective_value());
}

INSTANTIATE_TEST_SUITE_P(
        MyAlgorithm,
        ExactAlgorithmTest,
        testing::ValuesIn(get_test_params(
                // One or several algorithms (e.g. several parameter settings),
                // each run on all the instances.
                {
                    [](const Instance& instance) { return my_algorithm(instance); },
                },
                {
                    get_test_instance_paths(get_path({"test", "algorithms", "my_algorithm_test.txt"})),
                })));
```

Use them only for algorithms that are optimal on the listed instances: exact algorithms, and the other algorithms on the special cases where they are optimal (e.g. LPT on one machine with identical sizes).

## Optimal solutions

The optimal solutions of the test instances are stored with the instances, in the `tests` archive, as certificates `data/<instance path>_solution.json`. They are computed by `scripts/solve_test_data.py`: it runs an algorithm on the instances of the lists given with `--instances`, with a time limit (`--time-limit`, 1 s by default), and writes the instances solved to optimality (`"Optimal": true`) to the list given with `--output`. For each of these instances:
* if the instance has no certificate, the solution of the algorithm is stored as its certificate;
* otherwise, the value of the solution must be equal to the value of the certificate, and the certificate is kept. If the values differ, the script stops: two algorithms disagree on the optimal value of the instance, and one of them is wrong.

So an algorithm is tested against the certificates computed by other algorithms wherever they overlap, and each run of the script checks the new algorithm against all the existing certificates. The brute force (see [`brute_force.md`](brute_force.md)) runs first, since it is the simplest algorithm: most of the certificates of the instances with up to 8 jobs come from it. The certificates of the larger instances come from the algorithms that solve them, the MILPs and the tree search, and are only checked against each other.

The commands that generate the `.txt` files of the repository, in this order:
```shell
python3 scripts/solve_test_data.py --algorithm brute-force --max-jobs 12 --output test/algorithms/brute_force_test.txt --instances \
    data/test_makespan_identical_sizes.txt \
    data/test_{makespan,tft,twft,tt,twt}_{single,parallel,unrelated}{,_release_dates}.txt
python3 scripts/solve_test_data.py --algorithm tree-search --output test/algorithms/tree_search_test.txt --instances \
    data/test_makespan_identical_sizes.txt \
    data/test_{makespan,tft,twft,tt,twt}_{single,parallel}{,_release_dates}.txt
python3 scripts/solve_test_data.py --algorithm greedy-longest-processing-time --output test/algorithms/greedy_longest_processing_time_test.txt --instances \
    data/test_makespan_identical_sizes.txt
python3 scripts/solve_test_data.py --algorithm milp-rank-based-three-index-no-starts --output test/algorithms/milp_rank_based_three_index_no_starts_test.txt --instances \
    data/test_makespan_single.txt \
    data/test_makespan_parallel.txt \
    data/test_makespan_unrelated.txt
python3 scripts/solve_test_data.py --algorithm milp-rank-based-three-index --output test/algorithms/milp_rank_based_three_index_test.txt --instances \
    data/test_makespan_{single,parallel,unrelated}{,_release_dates}.txt
python3 scripts/solve_test_data.py --algorithm milp-rank-based-two-index-no-starts --output test/algorithms/milp_rank_based_two_index_no_starts_test.txt --instances \
    data/test_makespan_single.txt \
    data/test_makespan_parallel.txt
python3 scripts/solve_test_data.py --algorithm milp-rank-based-two-index --output test/algorithms/milp_rank_based_two_index_test.txt --instances \
    data/test_makespan_{single,parallel}{,_release_dates}.txt
```

`--max-jobs` only saves time, by skipping the instances that the brute force can't solve within the time limit. The commands need the solver built and installed in `install/` (`cmake --install build --config Release --prefix install`), with HiGHS for the MILP algorithms.

The lists of the MILPs and of the greedy algorithm, and the certificates of the makespan instances, were generated by the MILPs before the brute force existed. The brute force confirms the values of the 228 certificates of the instances it solves. 88 other certificates didn't match their instances (probably computed for an earlier version of the instances; no test used them): they have been removed, and the instances solved by the brute force have new certificates.

After generating new certificates, publish a new version of the `tests` archive (see `scripts/create_data_archives.py`).

## Before adding an algorithm

Besides the unit tests, compare the algorithm with brute force on many random small instances, built to hit the special cases (ties between processing times, idle time due to release dates, full batches, several machines), and with the best known values and bounds of the benchmarks (`data/data_*.csv`) on the instances too large for brute force: a wrong pruning rule or dominance rule, or a wrong proof of optimality, may only show up on a few instances.
